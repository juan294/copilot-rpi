## Deviations

### Phase 1

1. Re-decisions outside `decisions`.
   - Plan said: step 3 re-decides the 22 IDs that the 2026-11-14 intake deferred, in the decision file.
   - Found: 14 of those IDs did not change between `5920376` and `cec458a`, so the comparison does not print them. The checker rejects any decision ID that the comparison did not print as stale (`scripts/check-upstream.py:261-262`).
   - Chose: `decisions` holds exactly the 22 printed IDs. The 22 re-decisions sit in a separate top-level `prior_deferred_redecisions` array of the same file, which the checker ignores. The 8 IDs in both lists are marked "Superseded" in the re-decision array, or carry the 2026-11-14 delta rationale for the five overlapping release skills.
   - Why: the plan's decisions are recorded without weakening the checker.
2. "Adapted in Phase 3" items stay deferred in the lock.
   - Plan said: `rule:resource-lifecycle`, `rule:supabase`, `rule:rpi-details`, `instruction:rule-map`, `skill:macos-rules` and `skill:git-workflow` are adapted in Phase 3.
   - Found: an adapted lock entry needs an existing destination and its hash (`scripts/check-upstream.py:369-383`). `rule:resource-lifecycle` has no Copilot destination yet. `skill:git-workflow` maps to two files (rpi-implement and rpi-remediate), and a lock entry holds one destination. The other four would point at files whose content is not adapted yet, and three of them would share `templates/AGENTS.md.template`.
   - Chose: the re-decision records `adapted` with `lock_disposition: deferred`. The lock keeps them deferred, with a rationale that names the Phase 3 destination.
   - Why: design item 6 changes a destination in the phase that edits it. Phase 3 flips each entry to adapted with its destination and hash. Phase 3 must choose a single destination for `skill:git-workflow`, or leave it deferred with a rationale.
3. Engine and hook components keep `adapted` in the lock.
   - Plan said: `resource:configuration-engine` and `resource:distribution-engine` deferred; `resource:policy-engine` and `resource:prepush-gate` inapplicable.
   - Found: the lock records all four as adapted, with Copilot destinations (`rpi-config.py`, `rpi-distribution.py`, `rpi-hook.py`, `rpi-prepush.py`). Deferred or inapplicable lock entries must have null destinations (`scripts/check-upstream.py:381-382`), which would drop the destination hash tracking.
   - Chose: the re-decision applies the plan's disposition to the incoming cc-rpi delta, with `lock_disposition: adapted`. The lock adaptation notes say the delta is deferred or inapplicable. `hook:guard-bash` and `resource:package-engine` have no destination, so the lock takes the plan's disposition: guard-bash changes from deferred to inapplicable, and package-engine stays deferred.
   - Why: Phase 1 keeps every destination's bytes and hash.
4. The acceptance command with `--decisions` cannot pass after the repin.
   - Plan said: the comparison with `--decisions docs/decisions/2026-11-15-cc-rpi-2.2-sync-intake.json` against clean `cec458a` exits 0.
   - Found: after the repin the comparison has no differences, and the checker then rejects any decision file that is not `[]` ("future intake has stale decisions but no upstream differences", `scripts/check-upstream.py:233-237`). Exit 1.
   - Chose: run the decision comparison against the pre-repin lock (`087fab7`), where it exits 0. After the repin, run the comparison without decisions (no-op, exit 0) and the explicit `--source` check against the clean checkout (exit 0). The new test proves that the repinned lock blocks with the exact ID when a decision is removed.
   - Why: the checker is not weakened. The decision file is bound to the printed SHA and digest of the `5920376` comparison.
5. Version constant in the checker.
   - Plan said: repin the lock, as `33bb1b4` did.
   - Found: `33bb1b4` changed only the pin and hashes, because both pins were version 2.1.0. The checker compares the lock and supplied-source version against a literal `2.1.0` (`scripts/check-upstream.py:288`, `:480`).
   - Chose: one `PIN_VERSION = "2.2.0"` constant next to `PIN`, used by both checks.
   - Why: cc-rpi `cec458a` declares version 2.2.0, and the lock version must match the snapshot manifest (`scripts/check-upstream.py:328-329`).
6. Lint fixes in the plan files.
   - Plan said: track the plan, phase files and research report.
   - Found: once on disk outside the ignore rules, the plan and phase files failed the configured markdownlint (MD032 blank lines around lists, MD040 fence language).
   - Chose: blank lines around lists (markdownlint `--fix`) and `text` on the unlabeled phase-2 pseudocode fences. No wording changed.
   - Why: the local gate must pass all 10 checks.

### Phase 2

1. The workflow skill set is a constant.
   - Plan said: unknown skill names are `invalid`.
   - Found: copilot-rpi has 18 `rpi-*` workflow skills, but only the 16 named in Phase 3 get the overlay section. `rpi-debug` and `rpi-quality-review` get none. If the known set came from the installed copies, an overlay for those two would read as `inert` with an update fix that cannot resolve it (the class of cc-rpi 2.2.0 known issue S4 for lifecycle skills).
   - Chose: `OVERLAY_SKILLS` (16) and `LIFECYCLE_SKILLS` (4) constants in `rpi-lifecycle.py`. Any other name is `invalid` with a rename-or-remove fix. A test checks both sets against `templates/distribution.json`.
   - Why: the engine is standalone and an installed package carries no `distribution.json`. Phase 3 should add the test that the constant equals the skills that contain the section.
2. A missing installed copy is `inert`.
   - Plan said: `inert` means the installed copy lacks the overlay section.
   - Found: with no installation, or a skill that is not installed, there is no copy to inspect.
   - Chose: a missing copy is `inert`, with the update fix. Without a readable manifest profile, both `.github/skills/<skill>/SKILL.md` and `.github/prompts/<skill>.prompt.md` are inspected; each copy present must have the section.
   - Why: the overlay is valid but nothing reads it, and installing or updating ends that state.
3. Fix text for an unreadable manifest uses shell variables.
   - Plan said: the fix names the `check` command to run.
   - Found: `check` needs `--package` and `--profile`, and the manifest does not record the package path.
   - Chose: the printed engine command with `--target` filled in, followed by `--package "$package_dir" --profile "$selected_profile"`, the variable names used by `docs/migrations/v2.md` and `templates/setup-checklist.md`.
   - Why: this is the only runnable form without inventing a path.
4. `authored_sha256` placement is enforced.
   - Plan said: accept the field when it is 64 hex and reject it when malformed.
   - Chose: also reject it on any record other than a skill `SKILL.md` or prompt wrapper, in the receipt (`invalid package file record`) and in the manifest (`invalid Copilot ownership entry`).
   - Why: the field is only meaningful on those records, and a misplaced value would give overlays a wrong `current`.
5. Smaller choices.
   - `resource:diagnostics` shares its destination with `resource:lifecycle-engine`. `scripts/check-upstream.py:369-383` checks each entry's hash and has no one-entry-per-destination rule, so no change to the checker was needed.
   - The decision file `docs/decisions/2026-11-15-cc-rpi-2.2-sync-intake.json` is unchanged: it records the reviewed delta and is bound to the Phase 1 digest. The lock rationale records the Phase 2 change.
   - `drift` covers whole-file entries only. The `.vscode/settings.json` capability records are JSONC fields, not file baselines, and are left to `check`.
   - `overrides` is `null` when the file was not read. `Owner decision` must start with a `YYYY-MM-DD` date. An empty `## Declared overrides` section gives a reason. All are documented in `docs/project-overlay.md`.
   - New prose in `docs/project-overlay.md` and the added sentences keep one paragraph per source line, which the configured markdownlint allows (`MD013` is off).
6. Runtime location found during the real-render check.
   - Found: an installed target has only `manifest.json` and `baselines/` under `.rpi/copilot/`. The runtime stays in the rendered package (`package_files` skips `runtime:` records), although the `README.md` table describes `.rpi/copilot/` as holding the standalone runtime.
   - Chose: `docs/project-overlay.md` runs `diagnose` from `$package_dir/.rpi/copilot/runtime/`. The README table is unchanged in this phase.
   - Why: out of Phase 2 scope. Phase 3 must give `rpi-status` a command that works without the runtime in the target (the package or a blueprint checkout), and the README wording needs an owner decision or a separate fix.
