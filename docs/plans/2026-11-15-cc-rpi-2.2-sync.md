## Design

1. **The overlay contract matches cc-rpi.**
   - Path `.rpi/project/<skill>.md`. First line `<!-- rpi-overlay: skill=<skill>; written-against=<12 hex> -->`, then `## Procedure` and an optional `## Declared overrides`, as in cc-rpi `docs/project-overlay.md:14-20`.
   - copilot-rpi gets its own `docs/project-overlay.md`, written for Copilot.
   - The section text in each skill is cc-rpi's, unchanged, so the two blueprints read the same. It sits before each skill's first `##` heading.
   - rpi-status has no `##` heading, so the section is followed by a new `## Project orientation` heading.
2. **The overlay works the same in every profile.** The path is a repository path, not a resource path. The section reaches cli and agent-host as part of the byte-copied skill, and vscode-local through the embedded wrapper body (`templates/scripts/rpi-distribution.py:304-326`).
3. **Authored hash.**
   - The render receipt gets an optional `authored_sha256` field on the `SKILL.md` record of a skill component and on the `.prompt.md` record of a prompt component. Its value is the SHA-256 of `templates/skills/<name>/SKILL.md`.
   - Lifecycle copies the field into that manifest entry.
   - `load_state` accepts the field when present and well-formed (`templates/scripts/rpi-lifecycle.py:261-266`).
   - The no-op filter ignores it, as it already ignores `status` (`:546-549`), so an install without it stays healthy until its next real update.
4. **Reserved path.**
   - Products can already only target their `.github` destinations (`templates/scripts/rpi-lifecycle.py:182-201`).
   - `safe_relative` now also refuses `.rpi/project` and anything under it, comparing in lowercase, together with the two state roots (`:174-179`). This avoids cc-rpi 2.2.0's case-sensitivity known issue.
   - Tests prove that plan, apply, check, detach and rollback leave `.rpi/project` byte-identical.
5. **The `diagnose` command.**
   - `rpi-lifecycle.py diagnose --target <dir>`, also reachable through `rpi-distribution.py`. Read-only; JSON on stdout; exit 0 even when it reports problems.
   - The `installation` section reports whether a manifest exists, its profile and `source_version`, and the destinations whose bytes differ from their baseline (`modified`, `missing`).
   - `project_overlays` has one item per `.rpi/project/*.md`, with the same fields every time: `file`, `skill`, `status`, `reason`, `fix`, `written_against`, `current`, `header_line`, `overrides`.
   - Statuses, checked in this order:
     - `invalid`: not a regular file (symlinks included), uppercase name, larger than 64 KiB, not UTF-8, unknown workflow skill, or bad header;
     - `inert`: the installed skill copy lacks the overlay section;
     - `stale`: the header hash is not the current authored hash;
     - `present`.
   - It never prints overlay text and skips dotfiles. A lifecycle skill name is `invalid`.
   - These rules avoid cc-rpi 2.2.0 known issues S4-1 through S4-5 from the start.
6. **Intake first.** Phase 1 pins the lock to `cec458a` with every decision written down. A destination keeps its old bytes and hash until the phase that edits it, which also updates the lock hash and adaptation note. That keeps `upstream-provenance` green in every phase (`scripts/check-upstream.py:369-383`).
7. **Native probe.** Extend `tests/native/run_cli.py` with an `overlay` profile, based on the existing `cli` probe (`tests/native/README.md`).
   - The positive fixture has `.rpi/project/rpi-research.md` telling the skill to end with a random marker.
   - The negative fixture has no overlay.
   - A pass needs the native skill tool event and the marker in the positive run, and no marker in the negative run.

## Stuck states and recovery

| State | Who sees it, what they see | How it ends | Test |
| --- | --- | --- | --- |
| Checker blocks on a missing or stale intake decision | Maintainer: BLOCKED with the decision ID | Add the decision and rerun. The printed SHA and digest name the file to write | Existing `tests/test_upstream.py` blocked-decision cases, plus one for the new pin (Phase 1) |
| Overlay `invalid` | Adopter or agent: `reason` plus a `fix` naming the rename or header to write | Owner renames or fixes the file. Diagnose shows `present` next run | Phase 2 tests per invalid cause, asserting the fix text |
| Overlay `inert` | `fix` tells the adopter to update the installation | Update; diagnose shows `present` | Phase 2: old-copy fixture, then update, then `present` |
| Overlay `stale` | `fix` plus `header_line` | Write the printed header; diagnose shows `present` | Phase 2: write `header_line`, then `present` |
| Install without authored hashes | Nothing; `check` stays healthy | The next real update records the hashes | Phase 2: strip hashes, `check` stays healthy, update records them |
| `diagnose` cannot read the manifest | `installation.status: unreadable`, with the reason and the `check` command to run; exit 0 | Owner runs the printed `check` | Phase 2 corrupt-manifest test |
| Native probe blocked (no CLI, no credential, timeout) | Maintainer: a blocked receipt with a recovery action (existing harness behavior) | Install or authenticate, then rerun the printed command | Phase 4 fake-process tests for each block |
