# Research: copilot-rpi sync state against cc-rpi v2.2.0

- Date: 2026-11-15
- Repository: copilot-rpi, branch `main`, commit `087fab7` (clean except the owner's untracked `.summon`)
- Upstream compared: cc-rpi tag `v2.2.0`, commit `cec458a`, from a clean local clone
- Question: how copilot-rpi is structured for GitHub Copilot, which cc-rpi version and behavior it last took in, and what changed in cc-rpi since then (through v2.2.0, including project overlays), as input for a sync plan.

## Summary

copilot-rpi v2.0.0 (released 2026-09-29) is a native Copilot port with its own render profiles, ownership-aware lifecycle engine and upstream intake lock. Its last behavioral intake is cc-rpi `aa3ea57` (2026-09-28, before the cc-rpi 2.1.0 release). On 2026-11-14 a reference-only intake pinned cc-rpi `5920376` and deferred all 22 incoming behavioral deltas. The intake checker run against cc-rpi v2.2.0 reports 22 further changed components and blocks until each has a decision. Taken together, the behavioral gap is: project overlays (all 16 workflow skills, lifecycle reserved path and authored hash, diagnostics), proportional release verification with S1-S4 severities, the rpi-implement and rpi-triage stock rules, the resource-lifecycle rule family, lifecycle recovery repairs, launcher changes, and documentation. The pattern catalog did not change. copilot-rpi already has an optional destructive-only hook and an opt-in receipt gate. It has no `diagnose` command, although its rpi-status skill refers to one.

## 2. copilot-rpi structure relevant to the delta

- **Skills.** `templates/skills/` has 22 `rpi-*` skills plus `process-errors`. `rpi-debug` and `rpi-quality-review` are Copilot-only. cc-rpi's 13 domain skills are deferred in the lock. The allowed frontmatter fields are `name`, `description`, `argument-hint`, `user-invocable` and `disable-model-invocation` (`templates/scripts/rpi-distribution.py:28`). A bundled resource must be declared in the component and linked from the body (`templates/scripts/rpi-distribution.py:260-270`). Spot check: `templates/skills/rpi-plan/SKILL.md` matches cc-rpi except for Copilot additions and the missing `## Project overlay` section. No file in copilot-rpi or its snapshots mentions `.rpi/project`.
- **Render profiles.** `templates/distribution.json:5-15` defines `cli`, `agent-host` and `vscode-local` (version 2.0.0, 59 components). Skills install to `.github/skills/<name>` for cli and agent-host as a byte copy of SKILL.md plus resources (`templates/scripts/rpi-distribution.py:185-196`, `:298-303`). For vscode-local, the prompt wrapper embeds the full skill body, rewrites resource paths and copies resources under `.github/prompts/<name>/` (`templates/scripts/rpi-distribution.py:304-326`). Render writes the receipt `.rpi/copilot-render.json` (`:41`, `:415-426`).
- **Lifecycle.** `templates/scripts/rpi-lifecycle.py` provides plan, detach, check, apply and rollback (`:787-810`). State lives in `.rpi/copilot/` (manifest and baselines), with journals and plans in `.rpi/local/copilot/` (`:155-157`, `:408`, `:566`). A manifest entry records only `destination`, `component_id`, `base_hash` and `status` (`templates/scripts/rpi-lifecycle.py:441`). No per-skill source or authored hash exists. The only reserved paths are the two state roots (`:174-179`). `permitted_product_path` limits each component kind to its `.github` path (`:182-201`). There is no reserved-directory check equivalent to cc-rpi's `RESERVED_PROJECT_DIRECTORIES`.
- **Status and diagnostics.** There is no `diagnose` command. The distribution CLI offers validate, render and check-generated (`templates/scripts/rpi-distribution.py:506`). The skill nonetheless says "Use the distribution engine's read-only `diagnose` operation when installed; otherwise report that diagnostics are unavailable" (`templates/skills/rpi-status/SKILL.md:13-14`). The nearest report is lifecycle `check`: healthy or action-needed JSON with BLOCKED/WHY/FIX, exit 2 when action is needed (`templates/scripts/rpi-lifecycle.py:779-784`, `:836-841`).
- **Controls.** The pre-tool hook is already an optional destructive-only denylist. It passes through anything it cannot classify and states that it is not a security boundary (`templates/scripts/rpi-hook.py:1-10`). The pre-push receipt gate is opt-in through `"require_verification_receipt": true` (`templates/scripts/rpi-prepush.py:1-22`, `docs/native-policy.md:45-50`). The automation runner is report-only and never activates a scheduler (`templates/scripts/rpi-automation.py:1-7`).
- **Verification and release.** `scripts/verify-local.sh:5` runs `rpi-verify.py`, which has 10 checks (`:70-79`): unittest, verify-counts, verify-version, verify-prompts, distribution validate, check-generated, shellcheck, markdownlint, upstream-provenance and internal-links. CI `validate.yml` runs that gate on push and PR to `main`. Version sources are the CHANGELOG, `package.json`, `pyproject.toml`, the README badge and the manifest version (`verify-version.sh:116-127`). The repository applies itself through the cli profile into `.github/` (`templates/distribution.json:17-28`), and check-generated compares the bytes against the tracked receipt.
- **Native facts recorded.** The skill reads its referenced files from its own directory (`docs/compatibility.md:44-47`). The research agent declares `[read, search]` tools (`templates/github/agents/rpi-research.agent.md:4`). A CLI requalification found the model returning a fixture marker without a skill tool event, and the prompt now requests the tool call before file reads (`docs/plans/2026-09-28-copilot-blueprint-modernization-notes.md:207-212`). No recorded probe shows a Copilot skill reading an arbitrary project file such as `.rpi/project/<skill>.md` at run time. This is unverified.
- **Adopters.** No repository one level under `~/code` has a v2 copilot-rpi install (`.rpi/copilot/manifest.json`, `.rpi/copilot-render.json` or `.github/skills/rpi-*`). Only `wechat-miniapp` has legacy v1 prompt files, under `.github/prompts/`.

## 3. cc-rpi behavior changes since `aa3ea57`

Citations use the cc-rpi v2.2.0 checkout. The rpi-plan Stuck states and Consumer sweep sections, the denylist hook and the opt-in receipt gate already existed at `aa3ea57`, so they are not part of this delta.

1. **Workflow skills.**
   - Project overlay section in all 16 workflow skills (`25b105f`), for example `templates/skills/rpi-plan/SKILL.md:63`. The four lifecycle skills have none.
   - Proportional release verification with S1-S4 severities (`3320502`): `rpi-release/SKILL.md:50-70`, the severity table in `rpi-explore-release/SKILL.md:125-131`, `rpi-pre-launch:347` and `rpi-remediate:11,106,330`. Wave B selection in `rpi-adopt:71` and `rpi-bootstrap:59`.
   - rpi-implement commits deviation notes and cites plans by file name (`:64`).
   - rpi-triage treats an older report left by a failed run as an agent failure (`:37`) and an observability gap as YELLOW (`:391`).
   - rpi-status reports `project_overlays` (`:57`).
   - rpi-validate checks resource-lifecycle dispositions (`:29`, `4596be7`).
   - macos-rules has safe package guidance (`5920376`).
   - git-workflow follows resource-lifecycle before worktree removal.
   - rpi-detach and rpi-update are unchanged.
2. **Lifecycle engine.**
   - `.rpi/project` is reserved next to `.rpi/local` and `.rpi/baselines` (`templates/scripts/rpi-lifecycle.py:128-136`).
   - `source.authored_sha256` is recorded per SKILL.md entry (`:259`).
   - Provenance-only differences are bookkeeping, not drift (`:1172`).
   - Recovery repairs from the WB-L, WB2-L and WB2R3-L series:
     - detached status and a rollback-in-progress marker (`:1633`);
     - an `already-applied` result bound to the plan id (`:1241`, `:1377`);
     - a runnable repair for each conflict, with `move_aside_command` and `restore_command` that save the owner's copy (`:437-474`);
     - recording what an install created, and pruning only that on detach (`:907-924`);
     - mode drift.
   - A Python 3.11 guard (`templates/scripts/rpi-distribution.py:11`).
3. **Diagnostics.** `project_overlays` (`templates/scripts/rpi-diagnostics.py:610-672`, `:719`), mode drift (`:368-370`), and detached and interrupted statuses (`:268-275`).
4. **Policy hook and gate.** The hook is labelled best-effort, and every failure passes through. It adds a protected-tag rule (`templates/scripts/rpi-policy.py:105-107`) and normalises `refs/heads/` names. Unresolved push configuration is documented as an accepted limit (`docs/native-policy.md:24-33`). The gate adds per-commit cost, wider version tags, a NUL-safe dirty list and a hidden-change block. The enable command never overwrites a foreign hook (`docs/native-policy.md:64-200`).
5. **Launcher.** In `cc-rpi-update-agent.sh`:
   - a read-only Claude probe, falling back to Codex on a quota or authentication signal;
   - a kernel flock per project (`:115-157`);
   - supervised provider calls;
   - a probe timeout (`:42`);
   - Codex with network access off (`:439`).
   The other scheduler scripts changed for bash 3.2 only.
6. **Rules.** New `templates/rules/resource-lifecycle.md` (`4596be7`), with matching changes in `supabase.md`, `rpi-details.md` and `references/handoff.md`. testing, deployment-safety and webmcp are unchanged.
7. **Catalog.** `patterns/` is unchanged: 64 errors and 92 rules, nothing retired in 2.1.0 or 2.2.0. The rule-template count went from 6 to 7.
8. **Adopter docs.** New `docs/project-overlay.md`: the header format (`:14`), declared overrides (`:20`), statuses (`:30-39`) and limits (`:43`). Also new `methodology/resource-lifecycle.md`. Rewritten or extended: `docs/native-policy.md`, `docs/release-verification.md` and `docs/migrations/v2.md`.
9. **v2.2.0 known issues.** The release notes list two S3 and five S4 overlay and reserved-path issues (`CHANGELOG.md:29-37`).

## 5. Unresolved questions

- Copilot CLI and Agent Host have not been observed reading a project file named in a skill body, such as `.rpi/project/<skill>.md`. This decides whether the overlay works natively and what qualification evidence it needs.
- Where a vscode-local prompt wrapper, which embeds the skill body, should look for the overlay. The overlay section would sit in the embedded text, and the wrapper has no own directory for relative reads.
- Whether copilot-rpi diagnostics should be a new `diagnose` command, as rpi-status already expects, or an extension of lifecycle `check`.
- Which deferred components stay deferred. The cc-rpi launcher is Claude and Codex specific, and copilot-rpi has its own automation runner.
